# Skill 重构与优化

## 触发条件
当用户表达以下意图时加载本 Skill：
- 优化、重构、升级某个 Skill
- 转换 Skill 的书写格式或目录结构
- 将 Skill 翻译为其他语言
- 替换 Skill 中的数据来源或引用方式
- 对现有 Skill 进行版本迭代

## 工作流程

### 1. 确认目标项目
- 从上下文中提取用户提及的 Skill 名称。
- **必须**向用户确认："您确定要优化 `&lt;skill-name&gt;` 吗？"
- 获得明确肯定答复后，方可进入下一步。

### 2. 明确优化需求
询问用户具体的优化方向，例如：
- 仅调整格式/结构，不改动功能逻辑？
- 升级功能或扩展能力？
- 翻译为其他语言（目标语种）？
- 替换数据源或外部引用？

### 3. 分析现有项目
- 读取目标 Skill 的 `SKILL.md` 文件。
- 浏览项目目录结构，列出所有文件及其作用。
- 评估文件间的耦合程度，识别核心逻辑文件与辅助文件。
- 根据需求制定分步优化计划。

### 4. 创建隔离的工作副本
- 在用户当前工作目录下新建文件夹（如 `./skill-refactor-&lt;skill-name&gt;/`），用于存放修改后的文件。
- **严禁**直接修改原始项目文件。

### 5. 执行优化
- 按照优化计划逐步处理文件。
- 优先加载与当前步骤强关联的文件，避免一次性加载整个项目导致上下文溢出。
- 若涉及脚本代码的编程语言更换，**必须**事先征得用户明确同意。

### 6. 验证与修正
- 检查优化后的 `SKILL.md` 格式是否规范（YAML Frontmatter、Markdown 结构等）。
- 检查文件引用路径、变量名、示例代码的一致性。
- 如发现逻辑断裂或格式错误，立即修正并重新检查。

### 7. 交付结果
- 通知用户任务已完成。
- 简要总结：改了什么、为什么这样改、有哪些注意事项。
- 明确告知优化后文件的存放路径。

## 约束与红线

| 约束项 | 说明 |
|--------|------|
| 不碰原文件 | 所有修改仅在新建的工作副本中进行，原始项目保持只读。 |
| 功能守恒 | 未获用户明确授权，不得改变原有功能逻辑。 |
| 语言锁定 | 涉及脚本语言更换时，必须得到用户二次确认。 |
| 最小加载 | 单次上下文加载以必要文件为限，避免 Token 溢出。 |
